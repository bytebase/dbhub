---
title: "explain_sql"
---

Show the execution plan for a SQL statement without running it.

## Features

- **Never executes**: Only ever compiles/plans the statement — safe to enable regardless of the source's `readonly` setting
- **Per-dialect output**: Uses `EXPLAIN` on PostgreSQL, MySQL, and MariaDB, `SET SHOWPLAN_XML` on SQL Server (the estimated plan, as XML), `EXPLAIN PLAN` + `DBMS_XPLAN` on Oracle, `EXPLAIN indexes = 1` on ClickHouse, and `EXPLAIN QUERY PLAN` on SQLite (bare `EXPLAIN` on SQLite returns low-level bytecode, not a readable plan)
- **Opt-in only**: Not part of the default tool pair — must be explicitly enabled per source

<Note>
`explain_sql` is **opt-in**. Unlike `execute_sql` and `search_objects`, it is not enabled automatically when a source has no `[[tools]]` entries — add it explicitly (see [Enabling explain_sql](#enabling-explain-sql) below).
</Note>

## Usage

Pass a single SQL statement to explain. The tool adds the `EXPLAIN` prefix itself — do not include it in the input.

<CodeGroup>
```text Input
SELECT * FROM users WHERE status = 'active'
```

```text Sent to the database
EXPLAIN SELECT * FROM users WHERE status = 'active'
```
</CodeGroup>

Only a single statement is accepted (no `;`-separated batches), and the input must not itself begin with `EXPLAIN` or `ANALYZE` (or PostgreSQL's `ANALYSE` spelling) — both are rejected so the tool's own `EXPLAIN` prefix can never combine with a smuggled `ANALYZE` to actually execute the statement.

A leading PostgreSQL option list such as `(FORMAT JSON) SELECT ...` is accepted only when every option is one that cannot execute the statement: `VERBOSE`, `COSTS`, `SETTINGS`, `GENERIC_PLAN`, `BUFFERS`, `SERIALIZE`, `WAL`, `TIMING`, `SUMMARY`, `MEMORY`, `FORMAT`. `ANALYZE`, quoted option names, and any other option are rejected.

### ClickHouse

For a query, the tool sends `EXPLAIN indexes = 1`. Besides the plan's steps, the output lists for each table the parts and granules that its primary key, partition key and skipping indexes leave to read, which is how to tell whether a query will scan a slice of a table or all of it before running it. The output is along these lines:

```text
ReadFromMergeTree (analytics.events)
Indexes:
  PrimaryKey
    Keys: tenant_id, toDate(ts)
    Condition: and((tenant_id in [42, 42]), (toDate(ts) in [20454, +Inf)))
    Parts: 3/12
    Granules: 18/5321
```

To get another kind of plan, start the input with it: `ESTIMATE SELECT ...` (rows, marks and parts per table), `PIPELINE SELECT ...`, `SYNTAX SELECT ...`, or EXPLAIN settings of your own such as `actions = 1 SELECT ...`. Such input is passed on unchanged after `EXPLAIN`. No ClickHouse `EXPLAIN` runs the query, though planning may evaluate a constant subquery such as `(SELECT max(ts) FROM t)`.

<Tip>
Because plain `EXPLAIN` never executes the target statement, `explain_sql` is safe to run against write statements too. `explain_sql` on `DELETE FROM users WHERE id = 1` returns the plan without deleting anything.
</Tip>

## Enabling explain_sql

Add a `[[tools]]` entry with `name = "explain_sql"`. It takes no other options — no `readonly` or `max_rows` — since it's always read-only:

```toml
[[sources]]
id = "production"
dsn = "postgres://user:pass@localhost:5432/mydb"

[[tools]]
name = "execute_sql"
source = "production"
readonly = true

[[tools]]
name = "search_objects"
source = "production"

[[tools]]
name = "explain_sql"
source = "production"
```

See [Tool Configuration](/tools/overview#tool-configuration) for how `[[tools]]` entries work across multiple sources.
