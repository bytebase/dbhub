*Updated November 21, 2026*

DBHub exposes two database tools. How much smaller are their definitions than the tool sets in other database MCP servers?

This is a follow-up to the [token-efficiency comparison in our December 2025 review](/blog/postgres-mcp-server-review-dbhub#token-efficiency). We revisit the same three servers with current releases and a reproducible counting method. Because the method has changed, the results should not be read as a year-over-year reduction in token use.

We captured the tools from the latest npm releases available on November 21, 2026, and counted their definitions with a fixed tokenizer. The scripts, raw schemas, and per-tool results are [available in the repository](https://github.com/bytebase/dbhub/tree/main/benchmarks/token-definitions).

## Results

| MCP server | Configuration | Tools | Definition tokens | Size relative to DBHub |
|------------|---------------|-------|-------------------|------------------------|
| **DBHub 2.0.1** | Demo database, built-in tools | 2 | **261** | 1.0× |
| MCP Toolbox 1.18.0 | PostgreSQL prebuilt tool set | 29 | 3,901 | 14.9× |
| Supabase MCP 0.19.0 | Local npm server, default feature set, no project scope | 36 | 6,982 | 26.8× |

These are exact counts for the serialized definitions under **`cl100k_base`**, using `js-tiktoken` 1.0.21. They are not Claude token counts or a measurement of an entire agent session. A different tokenizer, client wrapper, or tool configuration will produce different numbers.

## What we counted

For each server, we initialized an MCP connection and retrieved every page of `tools/list`. For each tool, we kept `name`, `description`, and `inputSchema`. We sorted tools by name, sorted object keys recursively, serialized the array as compact JSON, and tokenized that string.

The count includes tool descriptions and input schemas. It excludes MCP transport envelopes, annotations, output schemas, server instructions, client-added name prefixes, conversation history, and query results. Clients decide which of these fields to send to their model; our benchmark holds the three selected fields constant across servers.

The [saved results](https://github.com/bytebase/dbhub/blob/main/benchmarks/token-definitions/results.json) include a SHA-256 hash of each counted payload and individual tool counts. Individual counts do not necessarily sum to the array total, because JSON separators and token boundaries differ.

## Why DBHub's definitions are smaller

DBHub combines database work into two tools:

- `execute_sql` runs SQL statements.
- `search_objects` finds schemas, tables, columns, indexes, and procedures. A name pattern and detail level control what it returns.

[MCP Toolbox](https://github.com/googleapis/mcp-toolbox) exposes separate PostgreSQL inspection and administration tools, including query plans, locks, replication, and database statistics. [Supabase MCP](https://github.com/supabase/mcp) covers a broader platform, including projects, branches, edge functions, and notebooks.

That broader scope costs tokens. Supabase's `create_notebook` definition alone is 1,220 tokens under this method. But these servers also provide operations that DBHub's built-in tools do not. This is a comparison of the listed configurations, not a claim that the products have identical capabilities. Restricting a server's tools or features can reduce its footprint.

## Full definitions versus session context

The table measures the full set of definitions. It does not mean every session loads all of them upfront.

Claude Code supports [MCP tool search](https://code.claude.com/docs/en/mcp#scale-with-mcp-tool-search), which can defer definitions until the agent needs them. Actual context use depends on the client, its configuration, and the tools discovered during the task. Smaller definitions still help when loaded, but the ratios above are not session-wide token or cost savings.

## Correcting the earlier benchmark

The previous version of this post reported 468 tokens for DBHub, 7,674 for Toolbox, and approximately 11,600 for Supabase using Claude Code's `/context` report. We have replaced those figures with the reproducible method above.

In our fresh run with Claude Code 2.1.330, `/context` labels its counts as estimates and rounds Supabase's largest tool to `1.5k`. Adding the displayed rows cannot recover an exact total. Publishing that sum as an accurate Supabase count would give readers false precision.

The new figures use a different measurement method, so their decrease is not evidence that the servers reduced their token use. For the same reason, we no longer present a numerical comparison with our [December 2025 benchmark](/blog/postgres-mcp-server-review-dbhub#token-efficiency).

## How to reproduce

From a checkout of the DBHub repository, recount the saved schemas:

```bash
cd benchmarks/token-definitions
npm ci
node count.mjs
```

This requires no database, API credentials, or model calls. The output should report **261**, **3,901**, and **6,982** tokens.

To capture fresh schemas from the pinned server releases, follow the [capture instructions](https://github.com/bytebase/dbhub/blob/main/benchmarks/token-definitions/README.md). Toolbox needs a reachable PostgreSQL database. DBHub uses its in-memory demo database. Supabase's local server accepts a placeholder token for initialization and tool discovery in this version; we did not call any Supabase tools or access an account. The hosted Supabase endpoint is outside this benchmark.

To try DBHub, see the [installation guide](/installation).
